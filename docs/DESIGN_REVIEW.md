# 架构问题处理结论

> 处理日期：2026-11-17  
> 对应文档：`ARCHITECTURE.md` 第 8 节  
> 代码版本：`server/main.py`

## 一、总体结论

这 9 个问题分成两类：

1. **可以通过实现消除或显著降低的**：摘要成本、空命中误导、重复写入、表膨胀、格式损坏、并发写入、撤销、中文词面检索。
2. **不能只靠本地工具解决的**：模型是否主动调用 `brief()`、真正的语义召回、跨设备同步冲突、模型漏记或错记。

处理原则是：**不把“提示词要求”包装成“系统保证”**。当前实现提升了失败可见性，并为误写、误删和并发写提供了安全边界，但不能声称已经解决平台钩子缺失的问题。

**工具形态（评审后调整）**：MCP 只暴露 5 个工具（`remember` / `brief` / `read` / `search` / `prune`）。
`validate` 和 `undo` 移到命令行（`python server/main.py validate|undo`），`archive` 合并进
`prune(dry_run=False, execute_archive=True)`。

原因：模型不会主动"检查格式"或"撤销自己刚写的"，这两个是管理员工具，占工具位只会增加模型选错的概率。
下面章节提到这三个能力时，指的是功能仍然存在，只是入口变了。

## 二、逐项结论

### 8.1 触发问题：无法在无钩子的客户端上可靠保证每轮读取

**结论：不能可靠保证。** MCP 只暴露工具，无法强制模型调用。提示词只能提高概率，不能提供系统级保证。

已处理：

- 新增 `brief(profile, recent_days)`，提供 `standard` 和 `minimal` 两档。
- `brief` 明确标注自己是“提示词级保障”，不冒充客户端钩子。
- 推荐工作流改为新回合先调用 `brief`。
- 当客户端支持预回合钩子或代理层时，应直接注入 `brief` 结果，而不是再依赖模型自主调用。

仍未解决：

- 模型完全跳过工具时，服务端不知道这一轮发生过什么。
- 唯一根治方式是客户端提供 pre-turn hook、MCP 中间件或宿主代理；这三个目标平台目前不开放。

因此产品文案应写“降低遗忘概率”，不能写“保证每轮读取”。

### 8.2 brief 的成本收益：改为两档摘要

**结论：不存在脱离任务的纯客观开关。** 判断标准只能是“本轮答案是否依赖此前用户专属状态”。

已处理：

- `brief(profile="standard")`：底表 + 最近 3 天 + 未完成待办。
- `brief(profile="minimal")`：底表 + 最近待办，适合上下文已明确、成本敏感的连续回合。
- 待办超过上限时明确提示还有未展开条目，不静默截断。

建议规则：

- 新会话、切换话题、引用过去、继续未完成任务、准备写决定：用 `standard`。
- 同一任务内的短追问、已知上下文的工具操作：可用 `minimal`。
- 完全自包含的问题才可以跳过；拿不准时读取。
- 判断依据不是“这轮看起来像代码”，而是“答案是否依赖过去两轮保存的用户状态”。

### 8.3 search 静默失败：不再把空结果解释为不存在

**结论：词面检索无法从设计上消除同义改写导致的漏召回。** 可以消除的是“空结果被误当成否定证据”。

已处理：

- `search` 返回值明确写出“未找到候选不等于表中没有”。
- 主表不超过 150 条且零命中时，自动回退全文，不再让模型靠空结果猜。
- 主表较大时返回目录、最近条目和下一步动作。
- 支持可选别名文件 `memory-table-aliases.md`，格式：
  `政策原文 = 政府文件, 政府公告`
- 搜索结果明确标记为“候选”，不是完整覆盖证明。

仍未解决：

- “政府文件”和“政策原文”如果没有共同字面片段，也没有别名，仍然不会互相命中。
- 真正的语义召回需要 embedding 或外部搜索服务，会破坏零依赖目标。

### 8.4 写入判断权：不逐条确认，但增加确定性防线

**结论：每条人工确认会导致产品不可用；完全信任模型会持续产生错记。** 当前采用“低风险静默写入、高风险强制理由、重复写入拦截”的折中。

已处理：

- `定了`、`否了` 必须提供 `why`。
- 同话题、同内容的完全重复条目拒绝写入，除非显式传 `force=True`。
- 写入前校验列宽、日期、话题和表结构。
- 写前自动备份。
- 新增 `undo()` 恢复最近一次写入前版本。
- `validate()` 检查主表、归档和别名文件。

仍未解决：

- 工具无法判断模型是否漏记了本应记录的事。
- 工具只能识别完全重复，不能可靠识别语义重复。
- 模型仍可能把“事实”放进“定了”。这属于模型判断错误，不是文件格式错误。

建议：高风险决定可以由模型先复述给用户，再调用 `remember`；不要要求所有事实和待办都人工确认。

### 8.5 表膨胀：归档而不删除

**结论：自动物理删除不适合作为默认能力。** 安全策略应是“冷热分层 + 可检索归档 + 永不删除”。

已处理：

- 新增 `archive(dry_run=True, older_than_days=180)`，默认只预览。
- 显式执行后，将旧流水条目移入 `memory-archive.md`。
- `底表`永不归档。
- 归档保留完整原行，`search` 默认同时检索主表和归档。
- `prune` 只报告和建议，不再暗示能自动安全删除。
- `prune(dry_run=False)` 仍不删除，避免旧接口产生不可逆误操作。

安全边界：

- 不自动删除。
- 归档前备份主表和已有归档。
- 先写归档、再改主表；即使第二步失败，最坏结果是重复，不会丢数据。

### 8.6 prompt caching：用公式判断，不拍一个固定条数

**结论：应同时考虑表大小、缓存价格、缓存失效和注意力位置，不能只看 token 数。**

可用近似判断：

- 设表大小为 `T` token。
- 每轮 `brief` 约 `B ≈ 500` token。
- 缓存读取价与普通输入价之比为 `r`。
- 每轮缓存表的成本约为 `T × r`。
- 当 `T × r < B` 时，静态缓存可能更便宜，即临界值约为 `T < B / r`。

例：若缓存读取价是普通输入价的 10%，临界点约为 5000 token。这个数只是示意，实际必须以模型和客户端计费规则为准。

但还有两个反向因素：

- 每次 `remember` 都会修改表，可能导致缓存失效。
- 工具调用返回在上下文末尾，位置优势通常比开头注入更强。

建议：默认使用 `brief`；只有大而稳定、很少写入、且客户端缓存机制明确时，才考虑整表放入缓存前缀。

### 8.7 跨设备：同步目录可行，但不是无冲突云存储

**结论：本地优先与自动跨设备同步不能同时免费获得。** 折中方案是把表放在网盘或 Syncthing 的本地挂载目录。

可采用：

- 表文件放在 OneDrive、Dropbox、Syncthing 等同步目录。
- 各客户端通过 `CONTEXT_TABLE_PATH` 指向该路径。
- 保留 `.context-table-backups` 一并同步，或定期单独备份。

限制：

- 当前文件锁只能保证同一主机上的多进程安全，不能解决两台设备同时编辑。
- 云盘同步冲突可能生成冲突副本，需人工合并。
- 不建议同时开启多个自动写入代理。

### 8.8 中文检索：2-gram 可做默认，但不等于语义检索

**结论：2-gram 适合零依赖词面召回，不能解决同义词问题。**

当前策略：

- 中文连续片段生成 2-gram。
- ASCII 单词和 `context-table` 这类连字符词同时保留整词与拆分片段。
- 使用查询覆盖率、条目覆盖率和精确子串加权排序。
- 可选别名文件处理已知同义词。

已知限制：

- 不是分词，可能产生片面匹配和误召回。
- 对同义改写、上下位词、错别字、繁简转换没有可靠召回。
- 表较小的时候，零命中全文回退比优化排序更重要。
- 是否上 embedding 应看真实使用数据；若表长期低于 150 条，不值得引入 API key 和依赖。

### 8.9 最坏失败模式：已增加锁定、原子写、校验、备份和撤销

已处理：

- 同主机的跨进程文件锁。
- 同目录临时文件 + `os.replace` 原子替换。
- 写前自动备份，保留最近 50 份。
- 写入前 schema 校验；结构错误时拒绝写入，但读取和诊断仍可用。
- `validate()` 输出具体错误。
- `undo()` 恢复最近写入前版本。
- 重复行检测默认拒绝写入。
- 8 个并发进程同时写入的测试通过，未丢条目。

仍不承诺：

- 不自动修复损坏的表，因为自动重写可能进一步丢数据。
- 网络文件系统上的锁语义取决于挂载和同步软件。
- 归档涉及两个文件，无法获得跨文件事务；采用归档优先写入以避免数据丢失。
- 备份清理只删除最旧备份，不删除主数据。

## 四、仍需外部条件才能完成的事

1. 客户端 pre-turn hook，才能真正保证每轮注入。
2. 真实语料上的检索评测，才能决定是否值得引入 embedding。
3. 跨设备写入协议或“单写者”约束，才能安全处理多设备并发。
4. 真实用户试用，才能确定高风险确认频率是否可接受。

## 五、关于“减少幻觉”的边界

原判断成立：表格法主要减少**事实型幻觉**，包括记错人名、数字、路径、时间、决定和已排除方案。

它不能修复：

- 推理链错误。
- 计算结果错误。
- 对用户意图的理解偏差。
- 模型没有调用工具时的漏读。
- 表内本来就写错的内容。

README 和宣传文案不能写“解决幻觉”，最多写“减少跨轮事实遗忘和事实型误记”。
